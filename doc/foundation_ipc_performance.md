# Foundation IPC 性能の基準値（2026-10-25、#173）

[ベンチマークの実行方法と計測契約](../foundation/tests/perf/README.md)。本作業は計測の追加で、IPCの仕様・本番カーネルの実装は変更していません。

## 条件と結果

基点は `07f4e4a37780ca5a983aaf450024ca8a32ef9a1e` に本ベンチマークを追加した作業ツリー。Clang 20.0.0git、`-O1`、16 MiB RAM。クライアントAPP／サーバーSERVICE、8回ウォームアップ、64往復のバッチを3回独立起動し、その平均の中央値を示します。各起動の値は同一でした。Cached の `reply_recv` の結果です。

| 要求/応答それぞれのデータ量 | VM ticks/往復 | VM µs/往復 | slot ticks/往復 | slot µs/往復 |
|---|---:|---:|---:|---:|
| 0 B | 18,626.3 | 388.05 | 17,473.7 | 364.03 |
| 32 B | 21,036.0 | 438.25 | 18,913.7 | 394.03 |
| 256 B | 24,312.0 | 506.50 | 22,237.9 | 463.29 |
| 4096 B、ページ先頭 | 80,850.2 | 1684.38 | 78,789.1 | 1641.44 |
| 4096 B、先頭+1 B | 426,738.1 | 8890.38 | 422,463.2 | 8801.32 |

空メッセージの処理量はVMで約2577往復/秒、slotで約2747往復/秒です。`reply` + `recv` ではそれぞれ400.92 / 376.73 µsなので、`reply_recv` により3.21% / 3.37%短縮します。syscall対照の `time_get(TICK_HZ)` は16.29 / 15.97 µsです。空メッセージでも約95%がカーネル会計に入り、全ケースでidleは0でした。トラップのassembly save/restoreは既存のCPU会計に従ってuser側に一部帰属するので、この95%は厳密なカーネル命令の比率ではありません。

同優先度（双方APP）でも空メッセージは `reply_recv` によりVMで3.19%、slotで3.18%短縮しました。大きいデータでは削減率が小さく、同優先度の非整列ケースには逆転もあります。timer/time sliceの位相も含むバッチ測定なので、全条件での一律な高速化は主張しません。

Pipelineでも両バックエンドでデータ検証と全11ケースが完了しました（独立起動は1回）。空メッセージの `reply_recv` はVM 490.82 / slot 459.70 µs、短縮率は2.98% / 3.17%。非整列4096 Bは整列時の5.39 / 5.49倍でした。CPUモデルが違う結果は、別の基準値として扱います。

Cached/VM/SERVICEを128反復でも確認しました（独立起動1回）。全IPCケースの1往復あたりの差は64反復比0.4%未満で、空メッセージの `reply_recv` は387.86 µs、非整列4096 Bは整列時の5.28倍です。syscall対照は15.51 µsに下がっており、特に短い対照ではsnapshotなどのバッチ固定費を無視できません。

## 改善の優先順位

1. **非整列コピー**。Cachedの非整列4096 Bは整列時のVM 5.28倍／slot 5.36倍。`foundation/kernel/mm.c` の `kmem_copy` はsrc/dstが両方4 byte整列した場合だけword単位のループに入り、それ以外は全量byteコピーします。ページ境界を持たないslotでも同程度の差が出るため、VMのページ処理だけでは説明できず、byte経路が有力です。src/dstの整列位置が一致する場合、先頭の数byteを処理してwordループへ移す改善を優先します。位置が異なるケース、短い長さ、末尾、ページ端を越える読み過ぎ・書き過ぎの禁止も別途検証する必要があります。このベンチマーク単独ではページ越えと非整列の寄与を厳密には分離していません。
2. **短いIPCの固定費**。データなしでも数百µsかかります。`ipc.c` の `deliver_call` と `write_recv` は同じ `fnd_recv` を再度読み、`read_msg`／受信／返信で構造体の検証とコピーを繰り返します。`mm.c` のVMソフトウェアページ変換、`proc_activate` のPTBR切替（TLB flush）、slotの保護領域設定、トラップ保存復帰を切り分けるのが次の段階です。VMの空IPCはslot比約6.6%増ですが、バックエンド全体の差であり、TLB単体のコストとは断定できません。検証済みの範囲の再利用や構造体の重複コピー削減を試し、保護・token・エラー時の契約を維持して比較します。
3. **サーバーループのsyscall削減**。既存の `reply_recv` で空IPCを約3%短縮できることが確認できました。`sys_ipc_reply_recv` は現在replyとrecvを順に呼ぶ実装で、専用fast pathはありません。fsサービスはすでにこのAPIを使用しています。未使用のサービスを調べた上で採用を検討し、専用fast pathはコピー・スケジューラの計測後に判断します。

`find_receiver`／`next_caller` は最大8スレッドを走査しますが、今回の2プロセス・1 outstanding callの結果から、その走査が支配的とは判断できません。複数クライアントの競合、キュー長、ハンドル転送、片方向だけの大容量、無関係なrunnableスレッド、優先度逆転、tail latencyは今後の追加項目です。ディスクやconsoleの処理を含むアプリケーション全体の速度も、この結果からは推定しません。

## 保存した証拠

[`foundation/tests/perf/baselines/`](../foundation/tests/perf/baselines/) のJSONに、CachedのSERVICE／同優先度とPipelineのSERVICE、追加の128反復確認を保存しています。数値はゲスト48 MHzクロックで、ホストの秒数ではありません。CIで絶対時間を閾値判定する用途より、同一条件での改善前後比較を意図しています。

## 同期DMAコピーの試作（#174）

`kmem_copy` に、重ならないMain RAMの256 bytes以上をDMAC ch1で同期転送する経路を追加しました。権限検証、VMの物理ページごとの分割、IPCの完了タイミングは従来どおりです。相対的な整列位置が一致する場合、先頭/末尾をCPU、本体を32-bit DMAで処理します。位置が異なる場合は8-bit DMAです。短いコピーと使用不可時はCPU経路を使います。

同じ変更後ソースを `--dma-min 0` と `--dma-min 256` でビルドして比較しました。Cached、SERVICEサーバー、64往復×3起動、`reply_recv` のバッチ平均の中央値です。両設定とも各起動の値は同一でした。

| 要求/応答のデータ量 | VM CPU µs/往復 | VM DMA µs/往復 | slot CPU µs/往復 | slot DMA µs/往復 |
|---|---:|---:|---:|---:|
| 0 B | 391.40 | 398.81 | 367.78 | 369.92 |
| 32 B | 441.02 | 450.45 | 396.77 | 398.90 |
| 256 B | 509.27 | 457.21 | 466.06 | 405.69 |
| 4096 B、ページ先頭 | 1688.25 | 499.45 | 1644.24 | 448.82 |
| 4096 B、先頭+1 B | 8893.89 | 553.14 | 8804.25 | 458.21 |

4096 B整列時の往復はVMで3.38倍、slotで3.66倍高速化しました。非整列時は16.08倍／19.21倍です。これは「往復全体」の倍率であり、DMA単体の帯域ではありません。256 BもVMで10.2%／slotで13.0%短縮しました。一方、CPU経路を使う0/32 Bにも分岐やコード配置等の費用が加わり、VMで約1.9〜2.1%、slotで約0.5〜0.6%増加しました。短い制御IPCの改善は引き続き別の課題です。

PipelineでもDMA有効の全11ケースをVM/slotで各1起動検証しました。VMの4096 Bは整列598.57 µs／非整列667.23 µs、slotは532.91／543.48 µsです。今回の変更後ソースによるPipelineのCPU専用比較は実行していません。

### console / fs への適用範囲

consoleのST_WRITEペイロード、fsのST_READ/ST_WRITE、disk I/OのVM bounce bufferとユーザーバッファの間など、カーネルの `mm_copy_*` を通る大きなコピーに適用されます。disk用ch0とコピー用ch1のenableビットを共存させました。

consoleのUTF-8/ANSI解析、文字ごとのPCG描画、キー入力の10 msポーリング、fs内部のキャッシュ・メタデータ処理やユーザー空間内のコピーは、この変更ではDMA化しません。console/fsが体感上の主な待ち時間であるという観察に対し、まずコピー部分を短縮する変更です。サービス全体の高速化率はまだ計測していません。次は大量のconsole出力とファイルread/writeの時間を、IPC転送、サービスのuser CPU時間、disk待ちに分けて測るのが有効です。

### 検証

- `python -m unittest discover -s foundation/tests/perf -p test_copy.py -v`：実DMACで全16組のsrc/dst整列、0〜8193 B、ガードbyte、重なり、無効BMC/DMAC、busy/stale error、ch0併走とIRQ/enable保持、非連続なVM物理ページ間の転送を確認。閾値256/1 × Cached/Pipelineの4構成が通過。
- VMの既存shell/console検証6件（banner、cat/cp、diskへのredirect、clear/scroll、ANSI、mode/redirect）が通過。追加のbulk I/Oも通過。
- slotでcat/cp、redirect、ANSI、bulk I/Oの4件が通過。bulk I/Oは非整列8193 Bのファイルwrite/read/EOF検証と4096 Bのconsole出力を行う。
- CachedではCPU専用／DMA、VM／slotを各3起動、PipelineではDMA、VM／slotを各1起動。生データは `baselines/2026-10-25-copy-*.json`。

同期方式なので転送中はカーネルを占有し、他のプロセスは実行しません。DMAエラー後のCPU再コピーは重ならない範囲だけに限定しています。非同期化する場合には、対象ページの寿命管理、終了時の停止、IRQ1の完了処理を別途設計する必要があります。
