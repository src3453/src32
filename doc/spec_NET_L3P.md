> **状態: 実装中。** 2026-11-22 に起草しました。§13 の「確認が必要な決定」が決まるまでは、バイト配置・番号・時間の具体値を変更できます。

> - TCP ブリッジと Foundation の `telnet`／`ssh` は L3P のストリームに移行済み（spec_NET_bridge 第 2 版）。

## 1. 目的と方針

CNET（[spec_NET.md](spec_NET.md)）はデータグラムを運ぶだけで、届くこと、順序、重複のなさを保証しません。L3P は CNET の上に置く共通のトランスポート層で、上位のプロトコル（CFP、telnet、今後のアプリ）が信頼性と暗号を各自で作らなくて済むようにします。

名前の「Layer 3」は、TCP/IP の 4 層モデル（リンク・インターネット・トランスポート・アプリケーション）の第 3 層、つまりトランスポート層に当たることを表します。OSI 参照モデルの第 3 層（ネットワーク層、CNET では spec_NET §4）とは別物なので、文書では L3P の層を「トランスポート層」と呼びます。

### 1.1 決定事項（提案）

| 項目 | 決定 |
|---|---|
| 名前 | L3P（Layer 3 Protocol） |
| 下位層 | CNET のデータグラム（PROTO `0x04`）。エンドポイントは CNET のアドレスとソケット |
| サービス | 必須: トランザクション（§5）、ストリーム（§6）。オプション: 暗号化（§7）、ストアアンドフォワード（§8）。§1.3 |
| 1 パケット | 1 データグラムに 1 パケット。トランザクションの 1 メッセージも 1 パケットに収める |
| TCP ブリッジ | **決定（2026-11-22）**：ブリッジと Foundation の `telnet`／`ssh` を L3P のストリーム（ソケット 23）に移す。両端ともこのリポジトリにあるので同時に切り替え、PROTO `0x40` はそのときに廃止する（互換のための併存期間は設けない） |
| オプションの配布 | **決定（2026-11-22）**：WAL `crypt` と `l3psf` を Foundation の既定のディスクに入れる。使うかどうかはアプリと設定（暗号化の要求、中継ノードの指定）で選ぶ |
| 実装場所 | 両端のソフトウェア。Foundation は WAL `l3p`（libcnet の上）、ホストは共有の Python モジュール。CNET カード・ホストの物理層・カーネルドライバは変えない（§10） |
| 保証すること | 完全性: 壊れた・重複した・抜けた・順序の乱れたデータを上位に渡さない。暗号化したときは改ざんも検出する。可用性: 相手に届いたことを確認できるか、決まった時間内に失敗として報告する |
| 保証しないこと | 相手が止まっている・経路が切れているときの配送（ストアアンドフォワードの中継ノードが受け取った後を除く）。暗号化しないときの盗聴・改ざん・なりすましへの耐性 |

### 1.2 層構成

```
CFP（spec_NET_FP.md）   telnet（spec_NET_bridge.md）   アプリ
        │ トランザクション        │ ストリーム            │ ストアアンドフォワード
        └──────────────┬──────────┴───────────────────────┘
L3P  結合の確立・暗号化（§4・§7）、再送・重複除去・順序・流量制御（§5・§6）
        │ PROTO 0x04 のデータグラム
CNET  ネットワーク層（CRC-16、ソケット）・データリンク層
```

### 1.3 必須とオプション

| 機能 | 区分 | 持たない実装 |
|---|---|---|
| 結合・トランザクション・ストリーム（§4〜§6） | 必須 | — |
| 暗号化（§7） | オプション | ENC を求める OPEN に RESET（ENC_UNSUPPORTED）を返す。自分から ENC を求めない |
| ストアアンドフォワード（§8） | オプション | 何もしなくてよい。§8 はトランザクションの上の別のサービス（ソケット 10）なので、持たない実装も他の部分はそのまま相互運用できる |

- オプションの機能を持つかどうかは、実装ごと・ノードごとに選べます。Foundation では、暗号化は WAL `crypt` を、ストアアンドフォワードは WAL `l3psf` を import したアプリだけが使えます（§10.1）。どちらも既定のディスクに入っています。
- ストアアンドフォワードを使うには、セグメントに中継ノードが必要です。中継ノードのないネットワークでは、L3P は結合を使う通信（相手がつながっているとき）だけを提供します。

## 2. CNET 上の位置

| 項目 | 値 |
|---|---|
| PROTO | `0x04`（CNET 標準域、spec_NET §4.2） |
| ポート | CNET のソケット番号をそのまま使う。サービスは既知のソケットで待ち受け、開始側は動的割当のソケットを使う |
| 既知のソケット | `9` CFP（トランザクション）、`10` ストアアンドフォワードの中継（§8）、`23` telnet（ストリーム。TCP ブリッジ、§1.1） |

1 つのソケットで複数の結合（§4）を同時に扱えます。結合はパケットの CONN で区別します。応答側は、パケットを要求の送信元アドレス・ソケットへ送り、DST_NET には要求の SRC_NET を使います（spec_NET_bridge §2 と同じ）。

## 3. パケット

### 3.1 共通ヘッダ（20 byte）

すべての数値は big-endian です。

| Offset | Size | Field | 説明 |
|---|---|---|---|
| 0 | 1 | VER_KIND | 上位 4 bit = version（`1`）、下位 4 bit = KIND（1 トランザクション、2 ストリーム。0 と他は予約） |
| 1 | 1 | TYPE | §3.2 |
| 2 | 1 | FLAGS | bit0 ENC（ペイロードを暗号化、§7）、bit1 FIN（ストリームの DATA だけ）。他は 0 |
| 3 | 1 | RSV | 0 |
| 4 | 4 | CONN | 結合番号。結合の外のパケットでは 0 |
| 8 | 4 | SEQ | トランザクション: XID。ストリーム: 先頭 byte の番号 |
| 12 | 4 | ACK | §5.3・§6.2 |
| 16 | 2 | WINDOW | §5.3・§6.2 |
| 18 | 2 | RSV | 0 |
| 20 | n | PAYLOAD | 平文は最大 1004 byte。暗号化したパケットは §7.3 の形で、上位のデータは最大 984 byte |

- 受信側は、version 不一致、予約欄が 0 でないもの、TYPE と KIND の組み合わせが不正なもの、知らない CONN のもの（RESET を返す場合を除く）を破棄します。
- 上位が使えるペイロードの大きさは `l3p_mtu()` で得ます（平文 1004、暗号化 984）。

### 3.2 TYPE

| 値 | 名前 | KIND | 説明 |
|---|---|---|---|
| `0x01` | OPEN | 1・2 | 結合の開始（§4.1） |
| `0x02` | ACCEPT | 1・2 | 結合の受け入れ |
| `0x03` | RESET | 1・2 | 拒否・中止。応答しない |
| `0x04` | CLOSE | 1・2 | 結合の終了の要求 |
| `0x05` | CLOSED | 1・2 | CLOSE への応答 |
| `0x06` | ACKONLY | 1・2 | 確認・キープアライブだけ。応答しない |
| `0x07` | HS | 1・2 | 暗号化の握手の 3 通目（§7.2） |
| `0x08` | READY | 1・2 | 握手の完了 |
| `0x10` | REQ | 1 | トランザクションの要求（§5） |
| `0x11` | RSP | 1 | トランザクションの応答 |
| `0x18` | UREQ | 1 | 結合なしの要求（§5.5）。ブロードキャスト可 |
| `0x19` | URSP | 1 | 結合なしの応答 |
| `0x20` | DATA | 2 | ストリームのデータ（§6） |

## 4. 結合

結合（association）は、2 つのエンドポイント（CNET のアドレスとソケットの組）の間の 1 本の通信路で、KIND（トランザクションかストリーム）、窓、再送の状態、暗号の鍵を持ちます。結合を始める側を**開始側**、待ち受ける側を**応答側**と呼びます。

### 4.1 確立

OPEN（CONN = 0、SEQ = 0、ACK = 0、WINDOW = 開始側が受け取れる窓）:

| Offset | Size | Field | 説明 |
|---|---|---|---|
| 0 | 4 | NONCE | 開始側が選ぶ乱数（0 以外） |
| 4 | 4 | OPTIONS | bit0 ENC（暗号化を求める）、bit1 PSK（事前共有鍵を使う、§7.4）。他は 0 |
| 8 | n | HS1 | ENC のとき Noise の 1 通目（§7.2）、なければ空 |

ACCEPT（CONN = 応答側が選んだ結合番号、WINDOW = 応答側が受け取れる窓）:

| Offset | Size | Field | 説明 |
|---|---|---|---|
| 0 | 4 | NONCE | OPEN の NONCE |
| 4 | 4 | OPTIONS | 受け入れたオプション |
| 8 | 2 | IDLE | 応答側の無通信タイムアウト（秒） |
| 10 | 2 | RSV | 0 |
| 12 | n | HS2 | ENC のとき Noise の 2 通目、なければ空 |

- 応答側は CONN に、推測しにくい 0 以外の値（乱数）を選びます。結合は CONN と開始側のアドレス・ソケットの組で識別し、組が一致しないパケットは破棄します。
- 開始側は ACCEPT が届くまで、§4.3 の間隔で同じ OPEN を送り直します。応答側は開始側のアドレス・ソケット・NONCE の組を覚えていて、再送された OPEN には新しい結合を作らずに同じ ACCEPT を返します。
- 同じ開始側のアドレス・ソケットから別の NONCE の OPEN が来たら、新しい結合として扱います（古い結合はタイムアウトで消えます）。
- 待ち受けていないソケット・KIND への OPEN、上限を超える OPEN、求めるオプションを受け入れられない OPEN には RESET を返します。
- ENC を受け入れた場合、§7.2 の握手が終わるまで REQ・DATA は送れません。ENC でない結合は、ACCEPT を受け取った時点で確立です。

### 4.2 RESET

ペイロード: REASON u16、RSV u16、MSG（UTF-8、0〜128 byte、表示用）。

| REASON | 意味 |
|---|---|
| 1 | NO_LISTENER（そのソケット・KIND で待ち受けていない） |
| 2 | BUSY（結合数の上限） |
| 3 | REFUSED（許可していない送信元。§9） |
| 4 | ENC_REQUIRED（応答側が暗号化を必須にしている） |
| 5 | ENC_UNSUPPORTED |
| 6 | AUTH_FAILED（握手の失敗、鍵の不一致） |
| 7 | UNKNOWN_CONN（知らない結合へのパケット） |
| 8 | TIMEOUT（再送の打ち切り） |
| 9 | ABORT（上位による中止） |

知らない CONN の REQ・DATA・HS・CLOSE を受け取った応答側は、RESET（UNKNOWN_CONN）を返します。RESET には応答しません。

OPEN を断る RESET（§4.1）は CONN = 0 で、SEQ に OPEN の NONCE を入れます。開始側はそれを、送信元と NONCE で自分の OPEN と結び付けます。それ以外の RESET の SEQ は 0 です。

### 4.3 時間

| 項目 | 値 |
|---|---|
| 最初の再送までの時間 | 300 ms |
| 再送間隔 | 再送のたびに 2 倍、上限 2400 ms |
| 打ち切り | トランザクション: 要求を最初に送ってから 15 秒。ストリーム: ACK が進まないまま 60 秒。OPEN: 15 秒 |
| 無通信タイムアウト（既定） | 120 秒。応答側が ACCEPT の IDLE で知らせる |
| キープアライブ | 結合が開いている間、何も送らないまま IDLE の 1/4 が過ぎたら ACKONLY を送る |

- 打ち切ったら、その結合は**壊れた**とみなし、RESET（TIMEOUT）を 1 回だけ送って捨てます。上位には `FND_E_TIMEOUT` を返し、以後のその結合の操作は `FND_E_STALE`（spec_NET_FP §7）になります。
- 無通信タイムアウトを過ぎた結合は、何も送らずに捨てます。

### 4.4 終了

- どちらの側も CLOSE を送れます。受け取った側は CLOSED を返して結合を捨てます。CLOSE を送った側は CLOSED か RESET を受け取るか、打ち切り（15 秒）で捨てます。
- 捨てた結合への再送された CLOSE には RESET（UNKNOWN_CONN）が返ります。CLOSE を送った側はこれも成功とみなします。
- トランザクションでは、応答を受け取っていない要求がある間は CLOSE を送りません。ストリームの正常な終わり方は FIN（§6.3）で、CLOSE は両方向の FIN の後に送ります。

## 5. トランザクション（KIND 1）

1 回の要求に 1 回の応答を返す RPC です。AppleTalk の ATP（exactly-once モード）に当たります。結合の中では、各要求は応答側の上位に**ちょうど 1 回、送った順に**渡されます。

### 5.1 要求と応答

- REQ の SEQ は XID です。開始側は結合ごとに 1 から 1 ずつ増やします。同じ要求の再送には同じ XID を使います。
- 応答側の上位は、渡された要求ごとに必ず 1 つの応答を返します。RSP の SEQ には要求の XID を入れます。
- 要求も応答も 1 パケットに収まらなければなりません（平文 1004 byte、暗号化 984 byte まで）。大きなデータは上位が分けて複数の要求にします。
- 要求を出せるのは開始側だけです。応答側から開始側への要求が必要なら、逆向きの結合を別に作ります。

### 5.2 実行順序

応答側は、1 つの結合の要求を XID の順に上位へ渡します。先の XID が届く前に後の XID が届いたら、窓（§5.3）の中なら保持して待ちます。上位は応答を返してから次の要求を受け取ります。そのため開始側は、応答を待たずに続けて要求を送っても、書き込みの後の読み取りなどの順序が保たれます。

### 5.3 窓と ACK

- 開始側は、応答を受け取っていない要求を最大 W 個まで送れます。W は ACCEPT の WINDOW（1〜4。CNET カードの受信キューがソケットあたり 8 データグラムのため）です。XID は「応答を受け取っていない最小の XID + W」未満でなければなりません。
- REQ と ACKONLY の ACK には、応答を受け取っていない最小の XID（全部受け取ったなら次に使う XID）を入れます。ACK は単調に増えます。RSP の ACK は 0 です。KIND 1 の WINDOW は、OPEN では開始側が希望する W、ACCEPT では許した W で、他のパケットでは 0 です。
- 応答側は ACK 未満の XID を「完了して忘れてよい」とみなし、受け取った REQ を次のとおり扱います。

| REQ の XID | 扱い |
|---|---|
| 最大の ACK 未満 | 破棄（遅れて届いた複製） |
| 応答済みで応答を保存している | 保存した応答を送り直す。上位に渡し直さない |
| 保持中、または上位が処理中 | 破棄 |
| 未受信で、最大の ACK + W 未満 | 受け付ける |
| 最大の ACK + W 以上 | 破棄（規約違反） |

- 応答側は ACK 以上の XID への応答をすべて保存します（最大 W パケット／結合）。
- 開始側は、応答を受け取っていない要求を XID の小さい方から §4.3 の間隔で送り直します。

### 5.4 打ち切りの意味

要求を打ち切ると、応答側はその XID を待ち続けるので、結合の後続の要求は進みません。そのため打ち切りは結合全体を壊します（§4.3）。打ち切った要求が応答側で実行されたかどうかは分かりません。上位は、必要なら新しい結合で状態を確かめ直します。

### 5.5 結合なしのトランザクション

UREQ／URSP は結合を作らずに 1 回だけ問い合わせる手段です（CONN = 0）。

- 開始側は SEQ に乱数を入れ、ブロードキャスト（NODE `0xFFFF`）にも送れます。URSP は同じ SEQ を返します。
- 重複除去も順序の保証もありません。開始側は §4.3 の間隔で送り直し、応答側の上位は同じ要求を複数回受け取ることがあります。そのため冪等な問い合わせ（一覧の取得、存在の確認など）だけに使います。
- ブロードキャストの UREQ には、各応答側が 0〜50 ms の乱数の遅延をおいて応答します。開始側は上位が決めた時間（既定 500 ms）待って集めます。
- UREQ と URSP は暗号化できません。

## 6. ストリーム（KIND 2）

順序どおりに届く両方向のバイト列です。AppleTalk の ADSP、TCP に当たります。TCP ブリッジのストリーム（spec_NET_bridge §3）を一般化したものです。

### 6.1 データ

- DATA の SEQ は先頭 byte の番号で、両方向とも 0 から始まります。データは 0〜1004 byte（暗号化は 984 byte）です。
- 受信側は、SEQ が次に期待する番号と一致する DATA だけを受け取り、それ以外は捨てます（go-back-N）。DATA を受け取るたびに（捨てた場合も、長さ 0 でも）ACK を返します。自分の DATA を送るときは、その ACK 欄で兼ねてかまいません。
- 送信側は確認されていないデータを保持し、§4.3 の間隔で ACK が進まなければ、確認されていない先頭から送り直します。再送のときにパケットの区切りを変えてかまいません。

### 6.2 ACK と流量制御

- ACK は次に受け取りたい byte の番号、WINDOW は ACK から先に受け取れる byte 数です。どちらも DATA と ACKONLY で有効です。
- 送信側は、相手の ACK + WINDOW を超える byte を送りません。さらに、確認されていない DATA を 4 パケットまでに抑えます（CNET カードの受信キューのため）。
- WINDOW が 0 の間、送信側は §4.3 の間隔で長さ 0 の DATA を送って窓を問い合わせます（これは打ち切りの計時に数えない）。

### 6.3 終わり

- FIN は 1 byte 分の番号を使います。FIN 付き DATA のデータの後の番号が確認されたら、その方向の送信は終わりです（半閉じ）。
- 両方向が終わったら、どちらかが CLOSE（§4.4）を送って結合を捨てます。
- 上位が中止するときは RESET（ABORT）を送ります。

## 7. 暗号化（オプション）

### 7.1 方針

- 暗号化は結合ごとに選びます。開始側が OPEN の OPTIONS.ENC で求め、応答側は受け入れるか（ACCEPT の OPTIONS.ENC）、拒むか（RESET の ENC_UNSUPPORTED）を決めます。応答側は暗号化を必須にでき、ENC のない OPEN を RESET（ENC_REQUIRED）にします。
- 握手は Noise Protocol Framework の **`Noise_XX_25519_ChaChaPoly_SHA256`**（PSK を使うときは `Noise_XXpsk3_25519_ChaChaPoly_SHA256`）です。独自の鍵交換は作りません。
- 握手の後の各パケットは ChaCha20-Poly1305（RFC 8439）で暗号化と認証をします。Noise の transport の暗黙のカウンタは順序どおりの配送を前提にするので使わず、パケットごとの番号（PN）を明示します（WireGuard と同じ考え方）。
- 暗号化はヘッダを隠しません（CONN・SEQ・ACK・WINDOW は見えますが、認証の対象なので改ざんは検出されます）。

### 7.2 握手

| 通目 | 運ぶパケット | Noise のメッセージ |
|---|---|---|
| 1 | OPEN の HS1 | `-> e` |
| 2 | ACCEPT の HS2 | `<- e, ee, s, es` |
| 3 | HS の PAYLOAD | `-> s, se`（psk3 なら `psk` も） |
| — | READY（PAYLOAD 空、ENC で暗号化） | 完了の確認 |

- prologue は ASCII `"L3P/1"`、KIND（1 byte）、OPEN の NONCE（4 byte）、応答側の CNET アドレス（4 byte）とソケット（1 byte）を連結したものです。アドレスは OPEN のデータグラムの DST_NET・DST_NODE をそのまま使います（開始側が NET 0 で送ったなら 0）。応答側の SRC_NET とは違うことがあるので、応答側も自分のアドレスではなく受け取った DST を使います。
- 開始側は 3 通目を送った時点で鍵を得ます。READY か、正しく復号できるパケットを受け取るまで、§4.3 の間隔で同じ HS を送り直します。応答側は、HS の再送には同じ READY を返します。
- Noise の split で得る 2 つの鍵のうち、1 つ目を開始側→応答側、2 つ目を応答側→開始側に使います。
- 握手が失敗したら（復号できない、鍵が許可されない）、RESET（AUTH_FAILED）を送って結合を捨てます。

### 7.3 暗号化したパケット

FLAGS.ENC を立てたパケットの PAYLOAD は次の形です。

| Offset | Size | Field |
|---|---|---|
| 0 | 4 | PN（その向きのパケット番号） |
| 4 | n | 暗号文（上位のデータ、最大 984 byte） |
| 4 + n | 16 | Poly1305 のタグ |

- PN は向きごとに 0 から 1 ずつ増やし、同じ値を 2 回使いません。同じ内容の再送も新しい PN で暗号化し直します。
- nonce（12 byte）は 8 byte の 0 と PN（u32）を連結したものです。追加認証データは 20 byte のヘッダと PN です。
- 受信側は、タグの検証に失敗したパケット、PN が直近 64 個の窓より古いか窓の中ですでに受け取ったものを破棄します（再送の重複除去は §5・§6 が別に行う）。
- PN が `0x7FFFFFFF` に達する前に、結合を閉じて新しく作ります。
- 握手を終えた結合では、OPEN・ACCEPT・HS と握手中の RESET 以外のすべてのパケットを暗号化しなければならず、ENC のないものは破棄します。RESET と CLOSE・CLOSED も暗号化して送ります。握手を終えた結合が平文の RESET を受け取っても、結合を捨てずに無視します（偽の RESET による切断を防ぐため）。相手が本当に状態を失った場合は、打ち切り（§4.3）で分かります。

### 7.4 鍵と認証

- 各ノードは長期の X25519 鍵（静的鍵）を持ちます。Foundation は `/etc/l3p/key`（UID 0、mode `0x0030`）、ホストの Python は `~/.cpt32/l3p/key` に置き、なければ初回に乱数（Foundation は `/dev/trng`）で作ります。
- 開始側は相手の静的鍵を known_hosts（Foundation は `/etc/l3p/known_hosts`、ホストは `~/.cpt32/l3p/known_hosts`）で確かめます。CNET のノード番号は動的なので、鍵は**サービスの名前**（mount 名や接続先の設定名など、上位が決める）と結び付けて覚えます。未知の鍵は指紋（SHA-256 の先頭 16 byte を 16 進）を表示して利用者が受け入れ、登録済みと違う鍵なら接続を中止します（TCP ブリッジの SSH ホスト鍵と同じ運用、spec_NET_bridge §5）。
- 応答側は、開始側の静的鍵の一覧（`--allow-key`）で相手を限れます。一覧がなければ、暗号化はしても相手は認証しません。
- PSK（32 byte）は、小さな閉じたグループで、事前に鍵を配った相手だけを通すために使います。
- 暗号化は CNET のセグメント上の盗聴と改ざんを防ぎます。ストアアンドフォワードの中継ノード（§8）は、通信路の暗号化を解いた内容を見ます（端から端までの暗号化は将来、§12）。

### 7.5 Foundation で必要なもの

`foundation/lib/crypt`（WAL `crypt` 1.1、`<foundation/crypt.h>`）に、握手と暗号化に要るものをそろえました: `cpt_x25519`／`cpt_x25519_base`、`cpt_sha256`（と init／update／final）、`cpt_hmac_sha256`、`cpt_hkdf_sha256`（Noise の HKDF は salt = ck、info なし、長さ 64／96 byte）、`cpt_chacha20poly1305_seal`／`_open`（§7.3 の暗号化）。

X25519 の 1 回は、llvm-src32 の -O2 のコードで約 1.5 秒（testbench の pipeline CPU、100 Hz の tick で 146 tick、2026-11-22 測定）です。開始側の握手は X25519 を 4 回（e の生成、ee、es、se）使うので約 6 秒かかり、そのうち ACCEPT を受け取ってから HS を送るまでが約 4.5 秒です。OPEN と HS の打ち切り（15 秒）には収まりますが、余裕は大きくありません。静的鍵の公開鍵は起動時に 1 回計算して覚えておきます。

## 8. ストアアンドフォワード（オプション）

### 8.1 方針

相手が今つながっていなくても、メッセージを中継ノードに預け、相手が後で受け取れるようにします。電子メールや UUCP に当たります。

この機能は**オプション**です（§1.3）。L3P の実装は持たなくてよく、中継ノードと、使いたいアプリのノードだけが実装します。

- 中継ノードは、L3P のトランザクション（ソケット `10`）でメッセージを受け付け、ディスクに保存してから成功を返します。成功を受け取った後の配送の責任は中継ノードにあります。
- 宛先は CNET のアドレスではなく**メールボックス**の名前です（ノード番号は再起動で変わるため）。受け取る側は、つながったときに中継ノードに問い合わせて受け取ります（プル型）。中継ノードは、登録された受け取り側の現在のアドレスに到着の知らせ（§8.5）を送れます。
- 第 1 版の中継ノードはホストの Python プログラム（`tools/l3p/l3p_relay.py`、既定ノード `0xFF03`）です。中継ノードを動かさなければ、この機能はネットワークに存在しません。中継ノード同士の転送は将来です（§12）。

### 8.2 メールボックス

- 名前は ASCII の英小文字・数字・`_`・`-`・`.` の 1〜31 byte で、照合は大文字小文字を区別しません。
- **所有者つきのメールボックス**は、作った結合の開始側の静的鍵（§7.4）に結び付きます。読み出し・削除・知らせの登録は、同じ静的鍵で暗号化した結合からしかできません。
- **開いたメールボックス**は、暗号化なしで作ったもので、誰でも読み出し・削除ができます。中継ノードが `--allow-open-boxes` を指定したときだけ作れます。
- メッセージの預け入れ（SUBMIT）は、どちらのメールボックスへも、暗号化の有無にかかわらずできます（許可は §9）。
- 中継ノードはメールボックスごとに容量の上限（既定 1 MiB）を持ちます。

### 8.3 メッセージ

| 項目 | 内容 |
|---|---|
| MSGID | 送る側が選ぶ 64 bit の乱数。メールボックスの中で一意 |
| 大きさ | 0〜65535 byte |
| TTL | 1〜604800 秒（7 日）。過ぎたら中継ノードが消す |
| TAG | u16。上位が内容の種類を表す（中継ノードは解釈しない） |
| FROM | 中継ノードが付ける。送った側の CNET アドレスと、暗号化した結合なら静的鍵の指紋 |
| 時刻 | 中継ノードが受け付けた時刻（i64 UNIX 秒） |

### 8.4 操作

中継ノードへのトランザクションの要求は、先頭 4 byte が `OP u8`、`RSV u8`、`RSV u16`、応答は先頭 4 byte が `STATUS i32`（0 以上が成功、負は Foundation のエラー番号）です。以下は続く部分です。

| OP | 名前 | 要求 | 応答 |
|---|---|---|---|
| `0x01` | BOX_CREATE | NAME_LEN u16、RSV u16、NAME | — |
| `0x02` | BOX_DELETE | NAME_LEN u16、RSV u16、NAME | — |
| `0x10` | SUBMIT_BEGIN | MSGID u64、TTL u32、SIZE u32、TAG u16、NAME_LEN u16、NAME | — |
| `0x11` | SUBMIT_DATA | MSGID u64、OFFSET u32、DATA | — |
| `0x12` | SUBMIT_COMMIT | MSGID u64 | — |
| `0x20` | LIST | NAME_LEN u16、RSV u16、COOKIE u32、NAME | NEXT u32、COUNT u16、RSV u16、各 MSGID u64・SIZE u32・TAG u16・RSV u16・時刻 i64・FROM（アドレス u32、指紋 16 byte、暗号化なしは 0） |
| `0x21` | FETCH | NAME_LEN u16、RSV u16、MSGID u64、OFFSET u32、COUNT u16、RSV u16、NAME | DATA |
| `0x22` | DELETE | NAME_LEN u16、RSV u16、MSGID u64、NAME | — |
| `0x30` | WATCH | NAME_LEN u16、RSV u16、SOCKET u8、RSV u8×3、NAME | — |

- 預け入れは SUBMIT_BEGIN → SUBMIT_DATA（OFFSET の順に、各最大 960 byte）→ SUBMIT_COMMIT です。COMMIT が成功するのは SIZE 分のデータがそろい、中継ノードがディスクに書き終えた後です（fsync してから応答する）。
- 同じ MSGID の BEGIN・DATA・COMMIT は何度送っても結果が変わりません。すでに COMMIT 済みの MSGID への COMMIT は成功、BEGIN は `EXISTS` です。COMMIT されないまま 10 分たった預け入れは捨てます。結合が壊れても、送る側は新しい結合で同じ MSGID の続きから送れます（BEGIN を送り直すと、受け付け済みの範囲を応答の STATUS（受け付け済みの byte 数）で返す）。
- 受け取る側は LIST → FETCH → 自分の保存を終えてから DELETE します。DELETE の前に壊れたら、同じメッセージを再び受け取ることがあるので、受け取る側は MSGID で重複を除きます（実質的に 1 回だけ届く）。
- 知らないメールボックスは `NOT_FOUND`、権限がなければ `ACCESS`、容量の上限は `NO_SPACE`、上限を超える SIZE・TTL は `BAD_ARG` です。

### 8.5 到着の知らせ

WATCH は、そのメールボックスにメッセージが届いたときに、要求した結合の開始側のアドレスと指定の SOCKET へ、結合なしの UREQ（PAYLOAD = `OP 0x80`、RSV×3、NAME_LEN u16、RSV u16、NAME）を送るよう登録します。受け取った側は URSP（空）を返します。

- 知らせは手がかりにすぎず、届く保証はありません。中継ノードは URSP が来るまで §4.3 の間隔で最大 5 回送ります。
- 登録は 1 時間で切れます。受け取る側は、つながっている間に定期的に登録し直します。ノード番号が変わったら登録し直します。

## 9. 許可と安全

- 応答側（サーバー、中継ノード）は、受け付ける送信元の CNET アドレスの一覧（`--allow ADDR`）と、開始側の静的鍵の一覧（`--allow-key`）で相手を限れます。暗号化しない結合の送信元アドレスは偽装できるので（spec_NET §7.2）、アドレスによる制限は誤接続の防止にすぎません。
- 暗号化を必須にする（`--require-encryption`）と、ENC のない OPEN を断ります。UREQ は暗号化できないので、必須にしても冪等な問い合わせ（CFP の輸出の一覧など）には答えます。上位は UREQ で秘密を返してはなりません。
- 受け取ったパケットはすべて信頼できない入力として、長さ・範囲・状態を検査します。知らない結合への応答は RESET だけにし、増幅を避けるため、RESET や URSP に RESET を返しません。
- 中継ノードは、1 つの送信元からの預け入れの速さと、預け入れ途中のメッセージの合計に上限を設けます。

## 10. 実装

### 10.1 Foundation（WAL `l3p` 1.0、`/lib/l3p.1.wal`）

`fnd` だけを import する WAL です。libcnet のコード（`foundation/lib/cnet/cnet.c`）は静的に含みます（プロセスの領域は 8 個で、`fnd`・`cnet`・`l3p` を import するプログラムは収まらないため）。ヘッダーは `<foundation/l3p.h>`、実装は `foundation/lib/l3p`。

**1.0 の実装範囲**: 開始側のトランザクション・ストリーム・結合なしの問い合わせ。結合の状態は呼び出し側の `l3p_assoc` に置き、関数は下表から少し変えています（`l3p_open(addr, socket, kind, opts, &a)` にまとめ、ストリームの読み書きは非ブロッキング、`l3p_ucall` は結果をバッファに並べる。WAL は関数ポインタを渡せないため）。正確な形は `<foundation/l3p.h>` と [API §9.6](spec_Foundation_API.md) を正とします。待ち受け（`l3p_listen` など）と暗号化は未実装です。暗号化を入れるときは `crypt` も import します（領域の数に注意）。

当初の計画（未実装の部分を含む）:

| 関数 | 内容 |
|---|---|
| `l3p_txn_open(addr, socket, opts, &a)` | トランザクションの結合を作る（握手まで待つ） |
| `l3p_txn_call(a, req, len, rsp, cap, &rlen)` | 要求を送って応答を待つ |
| `l3p_txn_send(a, req, len, &xid)`／`l3p_txn_wait(a, xid, rsp, cap, &rlen)` | 応答を待たずに続けて送る（窓の範囲） |
| `l3p_ucall(addr, socket, req, len, cb, ms)` | 結合なしの問い合わせ。ブロードキャスト可 |
| `l3p_listen(socket, kind, opts, &l)`／`l3p_accept(l, &a)` | 待ち受け |
| `l3p_txn_recv(a, buf, cap, &len, &xid)`／`l3p_txn_reply(a, xid, rsp, len)` | 応答側 |
| `l3p_stream_open(addr, socket, opts, &a)`、`l3p_read`、`l3p_write`、`l3p_shutdown` | ストリーム |
| `l3p_close(a)`、`l3p_info(a, &info)` | 終了、状態（相手、暗号化、相手の鍵の指紋） |

- 暗号化（オプション）は、WAL `crypt` を import したビルドだけが使えます。`l3p_txn_open` などの opts に ENC を指定し、使えなければ `FND_E_UNSUPPORTED` です。
- ストアアンドフォワード（オプション）は別の WAL `l3psf` 1.0（`/lib/l3psf.1.wal`、`l3p` を import する）にし、使うアプリだけが import します。関数は `l3p_sf_submit(relay, box, tag, ttl, data, len)`、`l3p_sf_list`、`l3p_sf_fetch`、`l3p_sf_delete`、`l3p_sf_watch` です。`crypt` とともに既定のディスクに入れます。
- 1.0 は結合ごとに動的割当の CNET ソケットを 1 個使います（多重化しない）。1 つのソケットで複数の結合を CONN で多重化するのは、待ち受けを実装するときに検討します。
- 再送とタイムアウトは、呼び出しの中で `/dev/cnet` の NONBLOCK の受信と tick で動かします。待ち受けを続けるサービスは、専用のスレッドで `l3p_poll` を回します。

### 10.2 ホスト（Python、`tools/l3p/`）

- `tools/l3p/l3p.py`: L3P と、CNET の UDP カプセル化・ノードの処理（PROBE への IN_USE、エコー）をまとめた共有モジュールです。今の `tools/cnet-bridge/cnet_bridge.py` の CNET 部分を移します。
- CFP サーバー（`tools/cfp-server/cfp_server.py`）、中継ノード（`tools/l3p/l3p_relay.py`）、ブリッジがこのモジュールを使います。

## 14. 実装時の検証項目

- 結合: OPEN の再送で結合が 1 つだけできること、NONCE の違う OPEN、RESET の各 REASON、CLOSE の再送、無通信タイムアウトとキープアライブ、打ち切りで結合が壊れて `STALE` になること。
- トランザクション: 要求・応答それぞれの損失・複製・順序の入れ替えで、各要求が上位にちょうど 1 回、XID の順に渡ること。窓の外の XID と ACK より古い XID の破棄。20% の損失で 1000 回の要求が正しく終わること。
- 結合なし: ブロードキャストの UREQ に複数の応答側が答え、遅延で受信キューがあふれないこと。
- ストリーム: 20% の損失で 1 MiB のバルク転送、窓 0 からの回復、半閉じ、RESET（ABORT）、未確認 4 パケットの上限。
- 暗号化（実装した場合）: Noise のテストベクタとの一致、握手の各通目の損失と再送、改ざんしたヘッダ・PN・暗号文の破棄、PN の再送窓、known_hosts の不一致での中止、`--allow-key` と PSK、暗号化必須での ENC なしの拒否。
- ストアアンドフォワード（実装した場合）: COMMIT の前後での中継ノードの再起動、同じ MSGID の再送、壊れた結合からの続き、TTL の期限、容量の上限、所有者つき・開いたメールボックスの権限、WATCH の知らせ。
- Foundation と Python の相互運用（双方向、暗号化あり・なし）。
