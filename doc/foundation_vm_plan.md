# vmfoundation 設計メモ（0.3）

状態: §12 のとおり実装済み（KAN-49）。以下は設計時の記録で、実装と違う点は §12 を優先します。当時は Extension V の仕様がなかった（`doc/spec_CPU.md` §Planning extensions に「V: Virtual Memory, MMU, TLB」の 1 行があるのみ）。したがって本書は「Foundation が V に何を求めるか」と「V が決まったときの Foundation 側の変更」を並べた叩き台で、どちらの契約も未確定。

## 1. 現状の制約（なぜ V が欲しいか）

| 現状 | 問題 |
|---|---|
| WAX v2/v3 は固定アドレス。ユーザーメモリは 12 MiB 以内の固定スロット（0〜6）で、1 プロセス 1 スロット | 同じアドレスにリンクされたアプリを同時に動かせない。スロット数が同時プロセス数の上限 |
| 保護領域は 8 個。プロセス切替のたびに 8 領域を全て書き直す | コード・データ・ヒープ・スタック・MMIO・WAL で 8 個を使い切る（`FND_E_REGION_LIMIT`） |
| 領域は物理アドレスそのもの | ヒープは連続領域にしか伸ばせない（`mem_grow` はスロット内で上限）。断片化対策がない |
| WAL は各プロセスのスロット内にコピー | 共有できない。WAL 数 × プロセス数だけ RAM を消費 |
| DMA（BMC/DMAC/IDC/VPU）は保護領域を検査しない | 現状は「カーネルが検証して実行」で回避している |

## 2. Extension V への要求（Foundation 側から出す案）

最小要求と、あると良い要求を分ける。

最小:
1. U モードの命令フェッチ・ロード・ストアを、ページ表で変換する。S モードは当面 identity（変換なし）のままにできる（カーネルを単純に保つため）。ただし S が任意のユーザーページを触る手段が必要（カーネルは物理アドレスで直接アクセスできるので、S=identity なら足りる）。
2. ページサイズ 4 KiB。RAM 16 MiB なら 4096 フレームで、フレーム表は 4 KiB 程度に収まる。
3. 2 段ページ表（10+10+12）。32bit アドレス空間をそのまま使える。1 段（4 MiB 領域）では細かすぎ・粗すぎるので 2 段が妥当。
4. PTE ビット: V（有効）、R/W/X、U（ユーザー可）、A（参照）、D（変更）。A/D はソフトウェア更新でもよい（フォルトで更新）。
5. ページフォールト: CAUSE に原因（read/write/fetch、not-present/protection）、フォルトアドレスを新 SR（`VFAULT`）で渡す。精密例外（Extension P §6.1 と同じ）。
6. ページ表基底レジスタ `PTBASE` と、`TLBFLUSH`（全消去）／ASID 付き消去。TLB はソフト管理（MIPS 型）ではなくハード walk を推奨（カーネルとフォルト処理が小さくなる）。
7. 既存の 8 領域との関係: V 有効時は領域チェックを無効にする（または二重に適用）。決めるべき点（§6 Q3）。

あると良い:
- ASID（プロセス切替で TLB 全消去を避ける）。無ければ切替ごとに全消去でも、現状の 8 領域書き換えより高くはない。
- 大きいページ（4 MiB）のスーパーページ。カーネルのマップや VRAM に便利。
- DMA は変換されない（物理アドレスのまま）。この点は変えない前提にし、カーネルが検証して物理アドレスに変換して発行する。

## 3. アドレス空間設計（案）

プロセスごとに 4 GiB の仮想空間を持ち、U からは下半分（0x00000000〜0x7FFFFFFF）のみ許す。

| 仮想範囲 | 用途 |
|---|---|
| `0x00001000–` | WAX 本体（固定アドレスのまま。プロセスごとに別空間なので衝突しない） |
| WAL 領域（例 `0x40000000–`） | WAL のコードページ（共有・R/X）とデータページ（プロセスごと・COW） |
| `0x5FFF0000` 下向き | スタック（ガードページ付き。フォルトで自動伸長可能） |
| ヒープ | WAX 末尾から上向き。`mem_grow` はページを追加するだけ |
| MMIO | 必要な window を U=1 の PTE でマップ（物理=実 MMIO）。8 領域の上限が消える |
| `0x80000000–` | カーネル（S は identity でもよい。U からは見えない） |

効果:
- 全 WAX が同じリンクアドレスで動く。スロット（§5.2）と `ADDRESS_CONFLICT`、`base_addr` を含むスロットの検査が不要になる。
- 12 MiB 制限は「物理 RAM の空き」だけが制限になる。ヒープは非連続でも伸長できる。
- WAL コードはフレームを共有（読み取りのみ）できる。データは COW か、読み込み時コピー。
- 保護領域の 8 個制限（`FND_E_REGION_LIMIT`）は ABI から消える（V が有効な環境では発生しない）。

## 4. 現行 ABI との互換と移行

方針: **ABI（spec_Foundation.md の syscall・IPC・handle）は変えない**。変わるのは §5（メモリと保護）と §9.5（WAX の読み込み）の内部だけ、という形にする。

- `mem_grow` / `proc_spawn` / WAX v2・v3 のバイナリはそのまま動く（固定リンクアドレスを維持するため）。
- `FND_E_ADDRESS_CONFLICT`・`FND_E_REGION_LIMIT` は、V 無効の環境でのみ返る（互換のため定義は残す）。
- ユーザーポインタ検証（§5.4）は、「領域内か」ではなく「そのプロセスのページ表で必要な権限が付いているか」に置き換える。カーネルは S=identity なので物理でなく仮想→物理の変換をソフトで行ってコピーする（IPC のコピーが仮想アドレスを跨ぐため、ページ境界ごとに変換が必要）。
- 拡張の判定は `CPUID` 命令で読む `CPU_FEATURES` で行う（決定 2026-10-22）。V のビットは未割り当てで、現在の空きは bit 9 以降（bit 8 が Extension P）なので bit 9 を提案する。起動時にそれを見て、V があれば vm モード、無ければ現行のスロットモード。両方を同じソースツリーで維持する（切替は kernel の `mm_*` 関数群の差し替え）。
- 実行形式: WAX v3 の WAL「位置独立」(R30 origin) は、V 環境では固定アドレスでも良くなる。ただし v3 のイメージはそのまま読める必要がある。

## 5. カーネルの変更点

1. **物理フレーム管理**（新規）: ビットマップ式のフレーム表。起動時にカーネル領域・stage1・MMIO を除外。ゼロ化は §5.4 の「付与前にゼロ」の規則を引き継ぐ（バイト単位ループは遅いのでワード単位）。
2. **ページ表**: プロセスごとの 2 段表。カーネルが維持する共有部分（カーネルマップ）をプロセスの表へコピー（またはスーパーページで共有）。
3. **コンテキスト切替**: `PTBASE` を書き、必要なら TLB を消去する（現行の「8 領域を全部書き直す」を置き換え）。スレッド間は不要（同一プロセス）。
4. **フォルトハンドラ**: スタックの自動伸長、ヒープの遅延割り当て（demand zero）。それ以外は現行どおり「そのプロセスのみ終了」（§3.4）。
5. **proc_spawn**: WAX を読み込むときにブロックごとにページをマップする。コードは R/X、データは R/W、WAL コードは共有。
6. **blk_io / DMA**: ユーザーバッファへ直接 DMA するなら、物理的に連続しないページを分割して複数回発行するか、カーネルのバウンスバッファ経由にする。最初はバウンスバッファ（現行と同じ）で良い。
7. **mem_grow**: ページを追加するだけ。上限は物理 RAM と各プロセスの上限（rlimit 相当を後で検討）。

## 6. 判断が必要な点（ユーザーへの質問）

- Q1. Extension V の仕様は誰が（いつ）定めるか。Foundation 側から上の §2 を要求として出し、`doc/spec_CPU_vm.md` を並行して書く進め方でよいか。
- Q2. ページ表は 2 段・4 KiB 固定でよいか（RAM が最大 16 MiB 前後なので、1 段のフラット表＋大きいページも選択肢）。
- Q3. V 有効時、Extension P の 8 領域は無効化か併用か。無効化の方が単純で、併用は「領域でさらに絞る」使い道がある。
- Q4. S モードも変換するか（カーネルが仮想空間で動く）。しない方が単純。しないなら U の全メモリを S が物理で触れる（現行と同じ）。
- Q5. TLB はハード walk かソフト管理か。エミュレータ実装（pipeline/JIT）の負担が違う。JIT は現状 U モードを interpreter に落とすので、V でも同様に落とす案が最小。
- Q6. 実行速度の目標。エミュレータの TLB をどう持つか（ソフトウェア TLB のキャッシュで十分か）。
- Q7. スワップ（ディスクへのページアウト）は対象外でよいか（まず「仮想アドレス空間とプロセス分離」まで、で良いと考える）。

## 9. V が無い CPU でのカーネル側エミュレーション（設計案のみ・スタブ）

決定（2026-10-22）: 将来 FPGA などで V の無い CPU に載せる場合に必要になるかもしれないため、今は設計案としてこの節に留め、実装しない。`mm_swap` は作らず、`mm` 層の差し込み口だけを意識する。

方針: 同じ Foundation ソースを V の有無で切り替える。`mm` 層（§7 手順 3）の裏に 3 つのバックエンドを置く。

| バックエンド | 条件 | 仮想アドレス空間 |
|---|---|---|
| `mm_hw` | `CPU_FEATURES` に V | ページ表による本物の仮想記憶 |
| `mm_swap` | V なし（新規） | 全プロセスが同じ仮想窓を共有し、切替時にカーネルが像を出し入れする |
| `mm_slot` | V なし（旧） | 物理スロット固定。**2026-10-25 に nommu（アリーナ方式）で置き換えた**（下の「状況」を参照） |

**エミュレーションの限界**: Extension P は「アドレスの許可判定」しかなく、アドレスの変換はできない。U モードの仮想アドレスは常に物理アドレスなので、フォルトで「別の物理ページへ読み替える」ことはできない。したがって実現できる範囲は次のとおり。

- できる: 同じリンクアドレスの WAX の同時実行（`mm_swap`）、プロセス分離、スタック・ヒープの自動伸長（連続領域のフォルトで拡張）、demand-zero。
- できない: 非連続ページのマップ、WAL コードページの共有（アドレスが固定なので）、スパースな空間、mmap。
- 現実的でない: U コードの完全なソフトウェア解釈（桁違いに遅い）。

**`mm_swap` の動き**:
1. 実行中プロセスの像（コード・データ・ヒープ・スタック）を、仮想窓（例 0x00800000–）に置く。
2. 別プロセスへ切り替えるとき、現在の像を退避領域へ DMAC でコピーし、次のプロセスの像を窓へ戻す（DMAC はカーネルが検証して実行するバスマスタなので、現行の方針と矛盾しない）。
3. 8 領域は窓の中だけを指す。像のサイズは窓の大きさ以下。
4. 切替コストは像サイズ比例。`proc_spawn` 直後や IPC 往復の多いサービス（fs・console）が窓を取り合うと遅くなる。サービスは常駐スロット（窓の外）に置き、アプリだけを窓で入れ替える混成が現実的。

**契約の切り方（提案）**: `spec_Foundation.md` の ABI は同一とし、機能を能力ビットで公開する（`sys_info` に VM 能力: `HW_PAGING` / `SWAP_WINDOW` / `SLOTS`）。アプリは WAL 共有や mmap に依存せず、`mem_grow` と固定リンクアドレスだけに依存するかぎり、3 つのどれでも動く、という「共通部分集合」を ABI として固定する。

**追加の質問**:
- Q8（回答済み）. V の無い環境は将来の FPGA 実装などで必要になり得るため、設計案として残す。実装は V 側が固まってから再検討する。
- Q9. 能力ビットを `sys_info` に足してよいか（ABI の追加で、後方互換）。

## 10. Extension V 仕様案（ユーザー提示 2026-10-22）と Foundation への影響

| 項目 | 仕様案 |
|---|---|
| VA / PA | 32 bit / 32 bit |
| ページ | 4 KiB、2 段（VPN 10+10 bit、offset 12 bit） |
| PTE | 32 bit |
| TLB | 16 エントリ、フルアソシアティブ、ラウンドロビン置換 |
| PTBR | 32 bit |
| ページフォルト | 例外 |
| DMA | 物理アドレス（変換しない） |
| MMIO | ページ属性 Device / Non-cacheable |
| 初版でやらない | Huge page、ASID、Swap、Demand paging |

### 10.1 この案から導ける Foundation の方針

- **ASID なし**: プロセス切替ごとに TLB 全消去。16 エントリなので、現行の「8 領域を全部書き直す」より安い。同一プロセス内のスレッド切替では消去しない（現行の領域の扱いと同じ）。
- **Demand paging なし**: ページフォルトはそのプロセスの終了（現行 §3.4 と同じ）。したがって `proc_spawn` と `mem_grow` が、必要なページを**先に全部マップ**する。スタックも spawn 時に WAX 宣言サイズ分を確保する。§5 の「スタック自動伸長」「遅延割り当て」は後の版に送る。
- **Swap なし**: 参照ビット（A）・変更ビット（D）は不要。PTE には予約として残す。
- **DMA は物理アドレス**: 現行どおりカーネルが検証して発行する。ユーザーバッファが物理的に非連続なら、バウンスバッファか、ページごとに分割して発行する。
- **MMIO 属性**: U に MMIO を付与する（§10.3）ときは Device 属性のページでマップする。8 領域の上限による制約は消える。ただし `0xFFFF0000` 以上は Extension P と同じく U から常に拒否する。
- **TLB 16 エントリ**: ワーキングセットが大きい処理（VRAM のコピーなど）でミスが増える。ミス処理が速い（ハードウェア walk）前提かどうかが性能の鍵。

### 10.2 仕様案が決めていない点（仕様化で埋める）

1. **TLB ミスの処理**: ハードウェアが PTBR からページ表を引く（推奨）か、ソフトウェアで埋めるか。ラウンドロビンは前者で自然。
2. **PTE のビット配置（提案）**: bit 0 V、bit 1 R、bit 2 W、bit 3 X、bit 4 U、bit 5 DEV（Device/Non-cacheable）、bit 6–7 予約（将来 A/D）、bit 8–11 OS 用、bit 31–12 PPN。下位段の PTE は R/W/X が全て 0 なら次の表へのポインタ（RISC-V 方式）。
3. **有効化と SR**: `VCTL`（bit 0 = 有効）、`PTBR`、`VFAULT`（フォルトアドレス）、TLB 操作用の SR（全消去／アドレス指定消去）。命令追加は不要にして `MTSR` で足りる形を推奨（Extension P の流儀に合わせる）。
4. **S モードの扱い**: 変換するか。推奨は「S は変換しない」（カーネルは identity のまま、U だけ変換）。この場合 `VCTL` は U にだけ効く。
5. **Extension P の 8 領域との関係**: V 有効時は U に対して無効化するか、AND で併用するか（推奨は無効化。ただし `0xFFFF0000` 以上の拒否は常に維持）。
6. **ページフォルトの CAUSE**: 提案 `0x8006_000k`（k = 1 read、2 write、4 fetch。bit 3 = 保護違反／未マップの区別など）。ベクタは bus error と同じ `0xFFFF0008` を共有（P の流儀）。フォルトは精密例外。
7. **CPUID**: `CPU_FEATURES` bit 9 を V に割り当てる（提案）。
8. **命令フェッチの TLB**: 命令と データで共通の 16 エントリか、分けるか。共通だと命令/データの競合が増える。
9. **キャッシュ付き CPU（Cached／cached-relaxed）との整合**: Device 属性ページはキャッシュしない。PTBR や PTE の書き換え後の TLB 消去の規則を明記する。
10. **エミュレータ実装**: pipeline・scalar・cached は共通のアドレス変換関数を `cpu_privilege.rs` の領域チェックの隣に置く。JIT は U を Cached へ落とす現行方針を維持。

## 12. 実装状況（2026-10-22、KAN-49）

§7 の手順 3〜4 を実装しました。仕様は `doc/spec_Foundation.md` §5.5、コードは `foundation/kernel/mm.c`/`mm.h` です。

- **mm 層**：`mm_slot`（現在は nommu のアリーナ方式。下の「nommu」参照）と `mm_vm` は `mm.c` の 2 つの実装で、`mm_init()` が最初の spawn で `CPUID` を見て選びます（`-D FND_MM_NOMMU_ONLY` で固定）。カーネルがユーザーの仮想アドレスを直接参照する場所をなくし、`proc_user_range_ok` と `mm_copy_*` に集めました。§8 の確認事項は、ポインタ検証が `proc_user_range_ok`、ユーザーバッファの複写が `ipc.c`・`proc.c`・`blk.c`・`trap.c` の数十か所だったので、そこをすべて置き換えました。
- **決めたこと（§6 の Q）**：Q2 2 段・4 KiB、Q3 領域は使わない、Q4 S は変換しない、Q5 ハードウェア walk、Q7 スワップなし。
- **§10.1 からの変更**：ヒープはページ境界から始め、`mem_grow` はページを足すだけ（領域を使わない）。DMA は `blk_io` だけで、64 KiB のバウンスバッファを使います。
- **仕様案の限界として残したもの**：権限はページ単位です。Foundation のイメージは `--page-align` で W^X を保ちます（`.rodata` の R 専用化は未実装）。MMIO の付与もページ単位で、ページ範囲が届く先の検査を追加しましたが、同じページの別レジスタには触れます。需要ページング、COW、WAL の共有ページ、7 個を超えるプロセスは未実装です。
- **Q9（`sys_info` の能力ビット）**：まだ足していません。`mm_swap` を実装するときに足します。
- **ツールチェーン**：`cpt32_cpu_features()`（`CPUID`）と、`cpt32_mtsr`/`mfsr` で SR `0x40..0x44` が使えます。パイプライン CPU は `CPUID` の暗黙の R1/R2 を interlock しないので、コンパイラは `CPUID` の後に NOP を 3 つ置きます。

## 13. nommu（アリーナ方式）への置き換え（2026-10-25）

V のない CPU の `mm_slot` を、nommu Linux のように**プロセスごとに連続した 1 つのアリーナ**を割り当てる方式に置き換えました。§9 の `mm_swap`（像の出し入れ）は採らず、再配置可能な実行形式で「同じアドレスにリンクされたアプリを同時に動かせない」を解決します。仕様は `doc/spec_Foundation.md` §5.2、画像形式は `doc/spec_WAX_v3.md` §3.1 です。

- 4 KiB ページのビットマップ（`[0x400000, RAM 末尾)`、最大 256 MiB）から、プロセスの全ブロック・WAL・スタック・ヒープ分の連続ページを first fit で取ります。固定アドレスの画像（v2 や `--protected`）は、その範囲を要求して取れなければ `FND_E_ADDRESS_CONFLICT` です。
- Foundation の全プログラムは `--pie`（再配置可能な WAX v3）です。カーネルは試しの基底で配置を計画してから確保し、`wax_rebase` で本番の基底に動かして、relocation table を適用します。
- `mem_grow` は nommu の `brk` と同じで、アリーナを動かせません。ヒープがアリーナの末尾にあり、上のページが空いているときだけ伸びます。大きなヒープが要る画像は `--heap-hint` で最初に求めます。
- 保護は Extension P の 8 領域（MPU）で、切替は従来どおりです。物理メモリを共有しない保証（ゼロ化・プール）もスロットのときと同じです。
- 残る制約：断片化は圧縮（アリーナの移動）で解消できません。プロセスは 7 個までのままです（スロットの数ではなくなったので、増やせます）。
