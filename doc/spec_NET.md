# CPT32 Network (CNET) 仕様

> **状態: 第 1 版を実装済み。** ホスト側の物理層は `src/devices/expansion/network.rs`、カードは `examples/wasm-cnet`、テストは `tests/cnet.rs` です。「決定事項」は 2026-11-21 の設計相談で合意した内容です。バイト配置、レジスタ番地、タイムアウトなどの具体値は第 1 版の実装に合わせたもので、互換性を壊す変更は VERSION を上げて行います。

## 1. 目的と方針

CPT32 同士をつなぐ、シンプルな独自ネットワークを定めます。TCP/IP 互換ではなく、AppleTalk（LLAP/AARP/DDP）のように小さなデータリンク層とネットワーク層だけを持ちます。

### 1.1 決定事項

| 項目 | 決定 |
|---|---|
| 互換性 | TCP/IP 非互換の独自プロトコル。将来、TCP/IP とのブリッジをセグメント上のノードとして追加できる余地を残す（§9） |
| 実装場所 | ネットワークスタックは**ハードウェア側**、つまり WASM 拡張カード（`doc/spec_WASM_expansion_card.md`）内に持つ。ゲストはソケット単位の MMIO インターフェイスだけを使う |
| ホストの役割 | 物理層だけ。カードが組んだフレームを送受信する最小限の host import を ABI v1 の後方互換拡張として追加する（§7） |
| 物理媒体 | UDP トンネル。既定はマルチキャストで同一 LAN 内に自動接続し、設定で列挙したユニキャスト相手にも送る |
| アドレス | 32 bit。上位 16 bit がネットワーク番号、下位 16 bit がそのネットワーク内のノード番号 |
| ネットワーク番号 | セグメント設定で固定（未指定なら 0）。ルーティングは最初の版に含めない |
| ノード番号 | 動的取得（プローブで重複確認）。設定で固定値も指定できる |
| 最初の版のサービス | データグラムとソケット（8 bit）だけ。信頼性のあるストリーム、名前解決、ルーティングは将来 |
| MTU | データグラムのペイロード最大 1024 byte |
| 検査 | ネットワーク層に CRC-16 |
| ゲスト I/F | ソケットごとの受信キュー、MMIO 上の TX/RX 窓（DMAC で転送可）、IRQ |
| 許可 | manifest でネットワーク利用を宣言し、`config.yaml` でそのスロットをセグメントへ接続したときだけ通信できる。未接続ならホストの外部通信はゼロ。カードはフレームを渡すだけで、宛先 IP を選べない |

### 1.2 層構成

```
ゲスト（Foundation / ベアメタル）
   │  MMIO（§6）: ソケット open/close/send/recv、IRQ
ネットワークカード（WASM）
   │  ネットワーク層（§4）: データグラム、ソケット、CRC-16、エコー応答
   │  データリンク層（§3）: ノード番号取得（§5）、リンクフレーム
   │  host import（§7）: net_send / net_recv / net_info
ホスト（エミュレータ）
   │  物理層（§8）: セグメント、UDP カプセル化、プロセス内 loopback
UDP / 他の CPT32
```

すべての複数 byte フィールドは big-endian（CPT32 の MMIO と同じ）です。

## 2. アドレス

アドレスは 32 bit の `NET.NODE` で、`NET` は上位 16 bit、`NODE` は下位 16 bit です。文字列表記は `0001.0012` のように 16 進 4 桁ずつドット（`.`）で区切ります。入力では先頭の 0 を省けます（`1.12`）。NET と NODE の区切りにコロンは使いません（以前の `0001:0012` 表記は受け付けません）。コロンは `telnet://HOST:PORT` のポート番号と同じく、ソケット番号の区切りに使います（下記の `NET.NODE:SOCK`）。

ローカルネットワーク（自分と同じネットワーク）のノードを指定するときは、NET を省いた短縮表記 `.NODE` または `NODE`（例: `.12`、`12`）を使えます。どちらも NET `0x0000`（「自ネットワーク」）として扱い、送信元と同じネットワークを指します。Foundation の `cnet_parse_addr`、シェルの `cnet`、デモの `chat` はこの表記を受け付けます。

ソケットまで指定するときは、アドレスの後にコロンで続けて `NET.NODE:SOCK` と書きます（例: `0001.0012:64`）。SOCK も NET・NODE と同じく 16 進で、`1–FE` を書けます（表示は 2 桁、入力では先頭の 0 を省けます）。アドレスの部分には上の短縮表記も使えます（`.12:64`、`12:64`）。ソケットを省いた `NET.NODE` は、使う側が決めた既定のソケット（エコーなら `04`、TCP ブリッジなら `17`（10 進の 23））を指します。Foundation の `cnet_parse_endpoint`／`cnet_format_endpoint`、シェルの `cnet send`、デモの `chat`、`telnet`／`ssh` の `-b` はこの表記を使います。

| 値 | 意味 |
|---|---|
| NET `0x0000` | 「自ネットワーク」。送信先に使うと、送信元と同じネットワークを指す |
| NET `0x0001–0xFFFE` | 通常のネットワーク番号 |
| NET `0xFFFF` | 予約 |
| NODE `0x0000` | 未割当／不定。送信元にも宛先にも使わない（プローブ中の送信元を除く） |
| NODE `0x0001–0xFEFF` | 通常のノード番号（動的取得の対象） |
| NODE `0xFF00–0xFFFE` | 予約。将来のルータ、ブリッジ、サーバなど既知の役割用（§9）。割り当て済み: `0xFF01` TCP ブリッジ（[spec_NET_bridge.md](spec_NET_bridge.md)）、`0xFF02` CFP サーバー（[spec_NET_FP.md](spec_NET_FP.md)）、`0xFF03` L3P のストアアンドフォワード中継ノード（[spec_NET_L3P.md](spec_NET_L3P.md) §8） |
| NODE `0xFFFF` | ブロードキャスト（同一セグメント内） |

ソケット番号は 8 bit です。文字列表記（`NET.NODE:SOCK`）では 16 進 2 桁で書きます。

| 値（10 進） | 16 進表記 | 意味 |
|---|---|---|
| `0` | `00` | 無効 |
| `1–127` | `01–7F` | 既知（固定割当）。`4`（`04`）はエコー（§4.3） |
| `128–254` | `80–FE` | 動的割当 |
| `255` | `FF` | 予約 |

## 3. データリンク層（リンクフレーム）

リンクフレームは 1 つのセグメント内でノード間を運ぶ単位です。

| Offset | Size | Field | 説明 |
|---|---|---|---|
| 0 | 2 | DST_NODE | 宛先ノード。`0xFFFF` はブロードキャスト |
| 2 | 2 | SRC_NODE | 送信元ノード。プローブ中は `0x0000` |
| 4 | 1 | TYPE | 下表 |
| 5 | 1 | RSV | 0 |
| 6 | 2 | LENGTH | 続くペイロードの byte 数 |
| 8 | n | PAYLOAD | |

最大リンクフレーム長は 8 + 16（ネットワーク層ヘッダ）+ 1024 = 1048 byte です。

| TYPE | 名前 | PAYLOAD |
|---|---|---|
| `0x01` | DATAGRAM | ネットワーク層データグラム（§4） |
| `0x81` | PROBE | ノード番号取得のプローブ（§5） |
| `0x82` | IN_USE | プローブへの「使用中」応答（§5） |
| その他 | 予約 | 受信側は破棄する |

受信側は、DST_NODE が自ノードかブロードキャストでないフレーム、LENGTH が実長と合わないフレーム、未知の TYPE を黙って破棄します。

## 4. ネットワーク層（データグラム）

### 4.1 ヘッダ（16 byte）

| Offset | Size | Field | 説明 |
|---|---|---|---|
| 0 | 1 | VER_HOP | 上位 4 bit = version（`1`）、下位 4 bit = hop count |
| 1 | 1 | PROTO | プロトコル型（§4.2） |
| 2 | 2 | LENGTH | ペイロード長 `0..1024` |
| 4 | 2 | CRC | CRC-16（下記） |
| 6 | 2 | DST_NET | |
| 8 | 2 | DST_NODE | |
| 10 | 2 | SRC_NET | |
| 12 | 2 | SRC_NODE | |
| 14 | 1 | DST_SOCKET | |
| 15 | 1 | SRC_SOCKET | |
| 16 | n | PAYLOAD | |

- CRC は CRC-16/CCITT-FALSE（多項式 `0x1021`、初期値 `0xFFFF`、反転なし）で、CRC フィールドを 0 とした 16 byte ヘッダと PAYLOAD を対象に計算します。hop count は経路上で変わるため、計算前に VER_HOP の下位 4 bit を 0 として扱います。
- 送信時の hop count は 0 です。将来のルータは転送ごとに 1 足し、15 に達したものは転送せず破棄します。
- 受信側は version 不一致、LENGTH 不一致、CRC 不一致を破棄します。宛先は、DST_NET が 0 か自ネットワークに一致し、かつ DST_NODE が自ノードかブロードキャストのときだけ受け入れます。
- 送信元は SRC_NET に自分のネットワーク番号（未設定なら 0）を入れます。

### 4.2 PROTO

| 値 | 意味 |
|---|---|
| `0x00` | 予約 |
| `0x01–0x3F` | CNET 標準（`0x01` = 汎用データグラム、`0x02` = エコー、`0x04` = [L3P](spec_NET_L3P.md)。L3P の既知のソケットは `9` CFP、`10` ストアアンドフォワード、`23` TCP ブリッジ） |
| `0x40–0x7F` | 予約。ブリッジ・カプセル化用（§9） |
| `0x80–0xFF` | アプリケーション定義 |

カードは PROTO の値を解釈せず、ゲストに渡します。例外はエコー（§4.3）だけです。

### 4.3 エコー

カードはソケット `4` 宛て、PROTO `0x02` のデータグラムに自動で応答します。PAYLOAD の先頭 byte が `1`（request）なら、先頭 byte を `2`（reply）に替え、残りを変えずに送信元へ返します。応答の宛先ソケットは要求の SRC_SOCKET です。ゲストはソケット 4 を open できません。

## 5. ノード番号の取得

カードはリンクが有効になったとき（§6 の `CONTROL.ENABLE`）に、ノード番号を次の手順で取得します。時間は仮想時間で、CPU クロック換算の cycle 数として `schedule_tick` で計ります。

1. 候補を決めます。設定の固定ノード（§8.2）があればそれを使います。なければゲストが書いた `NODE_HINT`（0 以外のとき）を使い、それもなければ `net_info` の乱数シードから `0x0001–0xFEFF` の値を選びます。
2. PROBE を `DST_NODE = 候補`、`SRC_NODE = 0x0000` で送ります。PAYLOAD は 4 byte の nonce（シード由来）です。20 ms おきに計 4 回送ります。
3. 待機中に次のどちらかが起きたら衝突です。
   - DST_NODE = 候補の IN_USE を受け取った。
   - 同じ候補への、自分とは異なる nonce の PROBE を受け取った。
   衝突したら、固定ノードの場合は `STATUS.CONFLICT` を立てて停止します。動的なら新しい候補で 2 からやり直します。動的な再試行の上限は 32 回で、超えたら `CONFLICT` です。
4. 最後の PROBE から 20 ms 衝突がなければ確定し、`STATUS.ADDR_VALID` を立てます。

確定済みのノードは、自分の番号への PROBE を受け取ったら、DST_NODE = その番号の IN_USE を返します。

## 6. ゲスト向け MMIO インターフェイス

オフセットはスロット内相対です。複数 byte レジスタは big-endian で、ゲストは上位 byte から読み書きします。コマンドは最後の byte を書いた時点で実行します。

### 6.1 共通レジスタ

| Offset | Size | 名前 | 属性 | 説明 |
|---|---|---|---|---|
| `0x0000` | 4 | ID | R | ASCII `"CNET"` |
| `0x0004` | 2 | VERSION | R | `0x0001` |
| `0x0006` | 2 | STATUS | R | bit0 LINK（セグメント接続あり）、bit1 PROBING、bit2 ADDR_VALID、bit3 CONFLICT |
| `0x0008` | 2 | CONTROL | R/W | bit0 ENABLE（1 にするとアドレス取得を開始、0 でリンク停止・全ソケット close）、bit15 RESET（書くと card reset と同じ） |
| `0x000A` | 2 | NODE_HINT | R/W | 動的取得の候補ヒント |
| `0x000C` | 2 | NET | R | 自ネットワーク番号 |
| `0x000E` | 2 | NODE | R | 自ノード番号（ADDR_VALID でなければ 0） |
| `0x0010` | 2 | IRQ_STATUS | R/W1C | bit0 ADDR（ADDR_VALID か CONFLICT への変化）、bit1 RX（いずれかのハンドルが空から非空になった） |
| `0x0012` | 2 | IRQ_ENABLE | R/W | IRQ_STATUS と同じ bit 配置 |
| `0x0014` | 2 | RX_READY | R | bit `h` = ハンドル `h` の受信キューが非空 |
| `0x0016` | 2 | MTU | R | `1024` |

IRQ 線は `IRQ_STATUS & IRQ_ENABLE != 0` の間 high です。IRQC は立ち上がりで pending を立てるので（`doc/spec_IRQC.md`）、ハンドラは IRQ_STATUS を W1C してから IRQC の PENDING を W1C します。

### 6.2 ソケットハンドル

ハンドルは 16 個（`h = 0..15`）です。ハンドル番号はソケット番号とは別です。ハンドル `h` のレジスタブロックは `0x0100 + h * 0x20` にあります。

| Offset | Size | 名前 | 属性 | 説明 |
|---|---|---|---|---|
| `+0x00` | 1 | SOCKET | R/W | open 前に書く。`0` なら動的割当。open 後は実際の番号を返す |
| `+0x01` | 1 | STATE | R | 0 closed、1 open |
| `+0x02` | 1 | CMD | W | 1 OPEN、2 CLOSE、3 SEND、4 RX_POP |
| `+0x03` | 1 | RESULT | R | 直前のコマンドの結果（§6.3） |
| `+0x04` | 1 | RX_COUNT | R | キュー内のデータグラム数 |
| `+0x05` | 1 | RX_DROPPED | R/W | キュー満杯で捨てた数（255 で飽和、書くと 0） |
| `+0x08` | 2 | TX_NET | R/W | 宛先 NET |
| `+0x0A` | 2 | TX_NODE | R/W | 宛先 NODE |
| `+0x0C` | 1 | TX_SOCKET | R/W | 宛先ソケット |
| `+0x0D` | 1 | TX_PROTO | R/W | PROTO |
| `+0x0E` | 2 | TX_LEN | R/W | ペイロード長 |
| `+0x10` | 2 | RX_NET | R | 先頭データグラムの送信元 NET |
| `+0x12` | 2 | RX_NODE | R | 送信元 NODE |
| `+0x14` | 1 | RX_SOCKET | R | 送信元ソケット |
| `+0x15` | 1 | RX_PROTO | R | PROTO |
| `+0x16` | 2 | RX_LEN | R | ペイロード長 |
| `+0x18` | 1 | RX_FLAGS | R | bit0 = ブロードキャストで受信した |

データ窓:

- TX バッファ: `0x10000 + h * 0x400`（1024 byte、R/W）
- RX バッファ: `0x20000 + h * 0x400`（1024 byte、R）。受信キュー先頭のペイロード。

どちらも通常の MMIO なので、DMAC の endpoint にできます。

受信キューはハンドルごとに 8 データグラムです。満杯のときに届いたデータグラムは捨て、RX_DROPPED を増やします。RX_POP で先頭を捨て、RX_* と RX バッファを次のデータグラムに更新します。キューが空のとき RX_* は 0 です。

送信は同期です。SEND を書くと、カードはヘッダと CRC を組み立てて `net_send` を呼び、その結果を RESULT に入れます。宛先が自アドレスなら、ホストへ出さずに自分の受信処理へ回します。ブロードキャストの送信は自分にも届きます。

### 6.3 RESULT

| 値 | 意味 |
|---|---|
| 0 | OK |
| 1 | BAD_STATE（open 済みで OPEN、未 open で SEND など） |
| 2 | IN_USE（ソケット番号が使用中、または 4 / 予約番号） |
| 3 | NO_SOCKET（動的割当の空きなし） |
| 4 | BAD_LEN（TX_LEN > 1024） |
| 5 | BAD_DEST（NODE 0、NET 0xFFFF など） |
| 6 | NO_ADDR（ADDR_VALID でない） |
| 7 | NO_LINK（セグメント未接続） |
| 8 | DROPPED（ホストの送信キューが満杯。現在のホストは送信を常に受理するので返らない） |
| 9 | NO_ROUTE（宛先 NET が自ネットワーク以外。ルータは第 1 版にない） |

## 7. host import（ABI v1 拡張）

### 7.1 manifest

manifest に任意フィールド `capabilities` を追加します。

```yaml
abi_version: 1
module: "wasm/cnet.wasm"
capabilities: [network]
```

`network` を宣言したカードだけが §7.2 の import を使えます。宣言せずに import すると起動エラーです。`capabilities` を知らない旧ホストは `deny_unknown_fields` によってロードを拒否します。ネットワークを提供できないホストでカードが黙って動くより安全なので、この挙動を仕様とします。宣言は許可ではありません。許可は §8 の設定で与えます。

### 7.2 import（namespace `cpt32_host`）

`network` カードは linear memory を `memory` として export する必要があります。

| Import | 型 | 契約 |
|---|---|---|
| `net_info` | `(i32 key) -> i32` | key 0: リンク状態（0 未接続、1 接続）。1: ネットワーク番号。2: 固定ノード（なければ -1）。3: 乱数シード（ホストがカード起動ごとに生成）。他の key はトラップ |
| `net_send` | `(i32 ptr, i32 len) -> i32` | memory 上のリンクフレーム（§3）を送る。0 = 受理、1 = 未接続、2 = 送信キュー満杯。範囲外ポインタや `len` が 8 未満か 1048 超ならトラップ |
| `net_recv` | `(i32 ptr, i32 cap) -> i32` | 受信キュー先頭のリンクフレームを書き込み、長さを返す。キューが空なら -1。`cap` < 1048 や範囲外ならトラップ |

任意の export として `cpt32_net_rx: () -> ()` を追加します。ホストは、カードの受信キューにフレームが積まれたあと、次の配送時点で 1 回呼びます（その間に何フレーム積まれても 1 回）。カードはその中で `net_recv` が -1 になるまで処理します。取り残したフレームは、次のフレームが積まれるまで通知されません。export がないカードは `tick` の中でポーリングします。カード reset ではホストの受信キューを捨てます。

ホストは、他カードや UDP から届いたフレームを即座にはカードへ渡しません。Bus の仮想時間を進める処理の中で（`run_scheduled_event` と同じ時点で）配送し、guest 呼び出しが直列になるようにします。受信待ちのカードは「現在 cycle が期限のイベント」として扱いますが、他カードのより後の tick 期限を隠しません。同じ cycle のイベント処理で別スロットへ新しいフレームが積まれた場合、Bus は同じ cycle のうちに最大 8 回まで処理を繰り返します。ホストのカードごとの受信キューは 64 フレームで、満杯なら新しいフレームを捨てます。

ホストは SRC_NODE の偽装や DST_NODE を検査しません（物理層は配線として振る舞う）。ホストが保証するのは、フレームが設定済みセグメントにしか出ないことだけです。

## 8. 物理層とホスト設定

### 8.1 セグメント

セグメントはリンクフレームが届く範囲です（AppleTalk の LocalTalk 1 本に相当）。種類は 2 つあります。

- **loopback**: 同じエミュレータ内のカード同士だけをつなぎます。testbench での決定的なテストに使います。
- **udp**: UDP datagram で他のエミュレータとつなぎます。

### 8.2 `config.yaml`

```yaml
network_segment:
  - name: "lan"
    network: 0x0001          # 省略時 0
    udp:
      bind: "0.0.0.0:32032"
      multicast: "239.255.32.32:32032"   # 省略でマルチキャストなし
      peers: ["192.168.1.10:32032"]      # 省略可
      segment_id: 1          # 同じマルチキャスト上の別セグメントを区別。省略時 0
  - name: "test"
    loopback: true

expansion_card:
  - slot: 2
    package: "plugins/cnet.cpt32card"
    network:
      segment: "lan"
      node: 0x0012           # 省略で動的取得
```

- `network` capability のないカードに `network` を書いた entry は起動エラーです。未知の key、存在しないセグメント名、範囲外のノード番号も起動エラーです。
- `network.segment` が未指定のカードは未接続（`net_info(0) = 0`、`net_send` は常に 1）です。ホストは、どのカードからも参照されないセグメントのソケットを開きません。
- 同じ `udp` セグメントに同じエミュレータ内の複数カードをつなぐと、ホストはプロセス内でも配送します。

### 8.3 UDP カプセル化

1 UDP datagram に 1 リンクフレームを入れます。

| Offset | Size | Field | 説明 |
|---|---|---|---|
| 0 | 4 | MAGIC | ASCII `"CNET"` |
| 4 | 1 | VERSION | `1` |
| 5 | 1 | FLAGS | 0 |
| 6 | 2 | SEGMENT_ID | `udp.segment_id` |
| 8 | 4 | SENDER | エミュレータ起動ごとの乱数 ID。マルチキャストで戻ってきた自分のパケットを捨てるのに使う |
| 12 | n | FRAME | リンクフレーム（§3） |

受信側は MAGIC・VERSION・SEGMENT_ID 不一致、自分の SENDER、FRAME 長不正を捨てます。ユニキャストの `peers` へは、マルチキャストと同じ内容をそれぞれ送ります。受信元アドレスで送信元を制限することはしません。外部から受信するデータはすべて信頼できない入力として、カードの検査（§3・§4）に任せます。

## 9. Foundation から使う

Foundation OS はカーネルドライバ `/dev/cnet` と WAL `libcnet`（`/lib/cnet.1.wal`）でこのカードを使います。1 本のストリームが 1 個のソケットです。契約は [Foundation API §9.6](spec_Foundation_API.md#96-cnet-ネットワーク-devcnet) を参照してください。2 台のエミュレータでチャットするデモは [`examples/cnet-chat`](../examples/cnet-chat/README.md) にあります。ホストの [TCP ブリッジ](spec_NET_bridge.md) を経由すると、シェルの `telnet`／`ssh` で外部のサーバーに接続できます。

## 10. 将来の拡張

- **TCP/IP ブリッジ**: セグメント上の 1 ノードとして作ります。予約ノード `0xFF00–0xFFFE` の既知の番号と既知ソケットで待ち受け、PROTO `0x40–0x7F` で IP やストリームをカプセル化します。外部 IP 接続、DNS、宛先制限、利用者の許可はすべてブリッジ側の責任にします。カードと物理層は変えません。ホスト側の独立プログラムで telnet と SSH を中継する [TCP ブリッジ](spec_NET_bridge.md)（ノード `0xFF01`、ソケット 23）を実装しました。第 1 版は独自のストリーム（PROTO `0x40`）でしたが、第 2 版で L3P のストリームに置き換え、`0x40` は使っていません。
- **ルーティング**: RTMP 風の経路交換で、複数のネットワーク番号をつなぎます。ルータは NET を学習し、ノードは「NET が一致しない宛先」をルータへ送ります。hop count はそのための予約です。
- **信頼性のあるストリーム**（ADSP 風）と**名前解決**（NBP 風）は、カード内に置く上位サービスとして追加します。

## 11. 実装時の検証項目

- loopback セグメント上の 2 枚のカード間で、データグラムの送受信、ブロードキャスト、エコーが通ること。
- ノード番号取得: 固定ノードの衝突で CONFLICT、動的取得の衝突で再試行、IN_USE 応答。
- CRC・LENGTH・version の不正、未知 TYPE、UDP の MAGIC／SEGMENT_ID 不一致の破棄。
- 受信キューあふれでの RX_DROPPED と、ホスト側キュー上限。
- 未接続のカードで外部通信が一切起きないこと（ソケットを開かない）。
- `capabilities` なしで network import を持つカードが起動エラーになること。
