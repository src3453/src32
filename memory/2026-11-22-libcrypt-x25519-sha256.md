# libcrypt 1.1: X25519、SHA-256、HMAC／HKDF、ChaCha20-Poly1305 AEAD

- 日付: 2026-11-22
- Issue: なし（ユーザー指示で作成せず）
- 目的: L3P の暗号化（doc/spec_NET_L3P.md §7、Noise_XX_25519_ChaChaPoly_SHA256）を Foundation で実装するための部品。

## 契約

- WAL `crypt` を 1.0 → **1.1**（エクスポート追加はマイナー版を上げる。ファイル名は `crypt.1.wal` のまま）。`crypt.exports`・`crypt.h`・`build.py` の `--abi-version` を揃える。
- 追加: `cpt_chacha20poly1305_seal/open`（RFC 8439 §2.8、出力は暗号文＋16 byte タグ、open はタグ一致のときだけ平文を書く）、`cpt_sha256`／`_init/_update/_final`（`cpt_sha256_ctx` は呼び出し側のメモリ、final が消去）、`cpt_hmac_sha256`、`cpt_hkdf_sha256`（`*dst_size` は欲しい長さ、最大 255×32）、`cpt_x25519`（低位数の点で全 0 になったら `CONDE_DATA`）、`cpt_x25519_base`。CONDE の「dst_size は容量を入れて書いた長さが返る」規約に従う（HKDF だけは長さの指定）。
- Noise の HKDF(ck, ikm) は `cpt_hkdf_sha256(salt=ck, ikm, info=空, 長さ 64/96)` と同じ。
- Poly1305 は増分（`poly_state`）に作り直した。AEAD が AD・パディング・暗号文・長さを分けて流すため。既存の `cpt_poly1305_auth` はその上の 1 回呼び出し。

## X25519 の実装と速さ

- TweetNaCl と同じ 16 bit × 16 limb（int64）。積は 32×32→64 で十分（limb は carry の間 ±2^20 以内）なので、`fmul` は int32 に落としてから掛ける。2 乗は `fsqr`（交差項を 1 回）、121665 倍は `fmul121665` に分けた。
- 1 回あたり testbench の pipeline CPU で約 146 tick（1.5 秒）。分ける前は 186 tick。開始側の握手は 4 回で約 6 秒。さらに速くするなら llvm-src32 の i64 加算・乗算の lowering か、10 limb（25.5 bit）表現が候補。
- 計測は `foundation/tests/crypt/kernel.c` を写して `on_tick` が終了時の tick を R1 に返すようにし、`cpt_x25519_base` を N 回呼ぶアプリの N=0 と N=4 の差を取った（testbench の `cycles=` はフレーム数で決まるので計測に使えない）。

## テスト

- `CLANG=... python -m unittest foundation.tests.crypt.test_crypt -v`: ホストで RFC 7748（§5.2、§6.1）、RFC 8439 §2.8.2、RFC 4231 case 2、RFC 5869 case 1、低位数の点、Python の `hashlib`／`hmac`／`cryptography` との乱数比較。ゲスト（scalar／pipeline）で SHA-256・HMAC・AEAD・X25519 の既知値。
- Windows のホスト DLL は `crypt.exports` の名前を全部 `/export:` するようにした（テストが読む）。
- 未確認: Noise プロトコル自体のテストベクタ（cacophony など）との一致。Python の `tools/l3p/l3p.py` の Handshake は自分同士でしか確かめていない。
