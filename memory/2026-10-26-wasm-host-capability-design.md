# WASMカード共通のホスト権限基盤の検討

- ネットワークに加え、ファイルアクセス、外部関数呼び出し、コマンド実行も対象にした設計検討。実装済みの機能や採用決定ではない。
- カード別APIの背後に共通の権限ブローカーを置き、manifestの要求とホスト側で保存するユーザー許可を分離する案。既存の読み取り専用package assetは従来の契約を維持し、外部ホスト資源を別管理する。
- 許可はカード内容のidentity、サービス、操作、対象範囲、有効期間、使用量上限で表す。slotやカードが自己申告する名前だけで認証しない。handleはカード・実行世代に紐づけ、各使用時に権限取消と所有者を検査する。
- ファイルは選択したファイル/ディレクトリをroot handleとして公開する。read/list/create/overwrite/delete等を分け、Windowsのjunction/reparse point、UNC、ADS、hard link、検査と使用の競合を考慮する。文字列のprefix判定やcanonicalizeのみを安全境界としない。
- 外部関数はホストで登録したサービスID・メソッド・型付き入出力で呼ぶ案。任意DLL path・symbol・pointerを渡すFFIは別扱い。ネイティブコードはWASMのfuelやmemory制限では隔離されないため、信頼する実装かOSで制約した別プロセスが必要。
- コマンドはユーザー管理の実行プロファイルに固定し、実行ファイル、引数スキーマ、cwd、環境、標準入出力、時間・出力・同時実行上限を定義する。shell文字列を初期APIにしない。許可した実行ファイルでも引数・設定・plugin読込から任意実行できる場合がある。
- 実行許可は子プロセスのファイル/ネットワーク制限を実現しない。別プロセス化や環境変数削除だけでも不十分。OS sandbox等を用意するか、制限のないホスト権限を与える実行として明示的に承認する必要がある。
- ファイル書込と実行・外部サービスの組合せによる権限拡大にも注意する。実行プロファイル・許可DB・実行ファイル等を通常の共有書込範囲に含めない。取消は将来の操作を止めるもので、書込済みファイルや送信済みデータを巻き戻すものではない。
- 共通要求状態はpending/completed/denied/cancelled等として非同期処理し、拒否は通常のエラー、ABI違反はfaultと分ける。reset/fault/取消で要求を無効化し、古い完了結果を世代番号で排除する。初期化・debug/audio等からの外部操作はホストで拒否する案。
- 実装時の検証対象は、拒否時の副作用ゼロ、他カードhandle・失効handle拒否、path脱出・リンク競合、引数による機能逸脱、子孫プロセス終了、取消後の結果配送抑止、旧ABI互換性。今回は設計検討のみで動作テストは実行していない。
