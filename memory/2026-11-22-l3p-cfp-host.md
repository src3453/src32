# L3P のホスト実装と CFP サーバー（Python）

- 日付: 2026-11-22
- Issue: なし（ユーザー指示で作成せず）
- 仕様: `doc/spec_NET_L3P.md`、`doc/spec_NET_FP.md`。実装: `tools/l3p/l3p.py`、`tools/cfp-server/cfp_server.py`。

## 実装で決めたこと（仕様に反映済み）

- OPEN を断る RESET は CONN = 0、SEQ = OPEN の NONCE。開始側はこれで自分の OPEN と結び付ける（元の仕様には結び付け方がなかった）。
- Noise の prologue の応答側アドレスは、OPEN データグラムの DST_NET・DST_NODE。開始側が NET 0（このネットワーク）で送ると、応答側の SRC_NET（例 1）と違うので、応答側の自分のアドレスを使うと握手が合わない。
- 結合の相手の照合は「ノードとソケットが同じで、ネットワークが同じかどちらかが 0」。NET 0 で開いた結合の ACCEPT は SRC_NET = 1 で返ってくるため。
- 握手中（開始側が HS を送って READY 待ち）は平文の RESET を受け付ける。握手が失敗した応答側はまだ鍵を持たず平文でしか RESET を送れないため。握手後の平文 RESET は無視するが、自分が CLOSE 中なら UNKNOWN_CONN を終了とみなす（§4.4）。

## 構成

- `l3p.py` に CNET の UDP ノード（Segment、Node）も入れた。今の `tools/cnet-bridge/cnet_bridge.py` はまだ自前のコピーを持つ（ブリッジの L3P 移行で置き換える予定）。`Node` のハンドラは `fn(src_net, src_node, src_socket, proto, body, dst_net, dst_node)`（DST はブロードキャスト判定と prologue に要る）。
- Endpoint ごとにタイマースレッド（20 ms）とワーカースレッドが 1 本ずつ。上位のコールバック（on_open、on_request、on_close、on_ureq）はワーカーで順に動くので、CFP サーバーは 1 スレッドで要求を 1 つずつ処理する（仕様 §9）。
- CFP の FS2 輸出は、メモリ上の `fs2.Volume` に変更を加え、構造の変更は即時、WRITE は CLUNK・SYNC・1 秒後に `check_image` を通して書き戻す。fs2 の操作が途中で失敗したら最後に書き戻したイメージに戻す（未書き戻しの WRITE は失われる）。`fs2.Volume.free_blocks()` はリストを返す（数ではない）。

## テストの注意

- `test_l3p.Lossy` を固定 seed で長いパイプライン転送に使うと、ある要求の再送が 9 回とも捨てられて打ち切りになった（L3P は正しく 9 回送っていた）。再送の周期と乱数の消費が噛み合うためと思われる。長いバルク転送は `Lossy(None, ...)`（OS の乱数）を使う。
- 再送の初期値 300 ms のため、20% の損失（往復で約 36% の要求が何かを失う）で 1 MiB（約 1100 要求、窓 4）に約 250 秒かかる。CFP のテストは 256 KiB にした（1 MiB も通ることは確認済み）。
- Windows の NTFS は名前が UTF-16 で 255 単位までなので、900 byte の名前はホストのディレクトリに作れない（EINVAL → `IO`）。テストはその場合だけ 900 byte の作成を省く。

## 検証（2026-11-22、Windows、Python 3.15、cryptography 50）

- `python -m unittest discover -s tools/l3p -v`: 23 件（約 9 分。20% 損失の 1000 要求・1 MiB ストリーム、暗号化、PSK、鍵の検査）。
- `python -m unittest discover -s tools/cfp-server -v`: 32 件（ホストのディレクトリと FS2 イメージの両方、約 7 分）。
